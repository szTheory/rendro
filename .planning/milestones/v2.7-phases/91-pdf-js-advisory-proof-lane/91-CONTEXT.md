# Phase 91: PDF.js Advisory Proof Lane - Context

**Gathered:** 2026-06-13
**Status:** Ready for research
**Source:** Accepted v2.7 milestone plan, v2.6 proof/evidence discipline, and Phase 91 roadmap scope

<domain>

## Phase Boundary

Phase 91 adds a pinned PDF.js advisory observation lane for maintainers. The lane records what a specific `pdfjs-dist` version observes about representative Rendro PDFs, including renderer version, Node version, page count, page dimensions, warnings, and optional first-page PNG hash.

This is not PDF.js GUI support, not browser support, not a required engine lane, not a Hex dependency, and not a Node/npm runtime requirement for Rendro core.

</domain>

<decisions>

## Implementation Decisions

### Advisory Scope
- Use wording like "pinned PDF.js advisory observations".
- Do not use "PDF.js support" unless a future support-matrix row explicitly proves and scopes that claim.
- Keep PDF.js graph-disconnected from required deterministic engine lanes.
- Preserve existing GUI-viewer support matrix boundaries for forms, signatures, long-lived signatures, and mobile viewers.

### Dependency Boundary
- Node/npm/pdfjs-dist may exist only as an advisory tool path, script fixture, or optional CI setup.
- Do not add Node, npm, or pdfjs-dist as a Hex dependency, Mix dependency, core runtime dependency, or required CI dependency.
- If a JS package file is introduced, it must live in an advisory/proof tooling boundary and be documented as maintainer-only.

### Observation Contract
- Record the exact PDF.js/pdfjs-dist version.
- Record Node version and invocation environment enough to reproduce observations.
- Record page count and page dimensions for every observed PDF.
- Record warnings and errors separately; warnings are observations, not automatic failures unless the observer script itself cannot run.
- Optional first-page PNG hash is allowed only if deterministic enough in the pinned setup and useful to maintainers.

### Evidence Fixtures
- Use a small representative PDF set already generated or easily generated by Rendro.
- Prefer committed compact observations over large binary churn.
- Avoid adding or regenerating broad launch artifacts unless necessary for the observation fixture.

### CI And Contracts
- CI lane, if added, must be advisory and graph-disconnected from required engine lanes.
- Docs-contract or guardrail tests must prevent overclaiming: PDF.js wording must remain advisory and cannot promote GUI-viewer support.
- Any public docs touched in Phase 91 must keep exact language narrow; broader guide updates belong to Phase 92.

### the agent's Discretion
- Whether the observer is a Mix task wrapping a JS script, a direct script under `scripts/`, or a maintainer command with fixtures, provided the dependency boundary is explicit and tested.
- Exact fixture set, file locations, and JSON schema shape for observations.
- Whether first-page PNG hashing is included now or deferred if deterministic setup is too fragile.

</decisions>

<specifics>

## Specific Ideas

- Prefer a command that writes deterministic JSON observations under `priv/pdfjs_observations/` or a similarly explicit advisory path.
- Include fields such as `observer`, `pdfjs_dist_version`, `node_version`, `recorded_at`, `pdf`, `page_count`, `pages`, `warnings`, `errors`, and optional `first_page_png_sha256`.
- Add a docs-contract test that fails on banned phrases like unqualified "PDF.js support" if Phase 91 introduces public copy.
- Add a guardrail test ensuring any PDF.js workflow context is not listed under `required_contexts`.
- Keep fixture count small: one simple text PDF, one multi-page/page-context PDF, and optionally one form/signature fixture only if it does not imply GUI support.

</specifics>
