    **`## BASE-04 — P0–P3 Recommendation Report` section:**
    Write recommendations in descending priority order. Each item MUST include all 7 fields: Category, Issue, Proposed change, Expected impact, Risk, Rollback, Target phase.

    **P0 — Decompose the `mix ci` monolith into parallel named jobs/steps (flagship recommendation)**
    - Category: Performance
    - Issue: All of `format → hex.build → compile → test → docs → credo → dialyzer` runs in a single opaque "Run CI" step. This means: (1) the API cannot see the inner split; (2) zero parallelism exists (format/test/credo could run in parallel); (3) a dialyzer failure retakes 6+ minutes of earlier work; (4) BASE-05 job-summary instrumentation is needed now because there is no per-step timing otherwise.
    - Proposed change: Split `mix ci` into named steps (Phase 109 adds caching first; Phase 111 restructures the job topology). Comparable szTheory repos: mailglass (Format/Compile/Support-Contract), threadline (format→credo→compile→test, named steps), lockspire (qa/sast/docs/audit/test).
    - Expected impact: Per-step timing visible in API and job summary; foundation for parallelism; faster feedback on lint vs test vs dialyzer failures.
    - Risk: Low — decomposition is additive; any job can still serialize if needed.
    - Rollback: Revert the job-topology YAML to the current single-step `mix ci`.
    - Target phase: 109 (caching prerequisites) + 111 (topology implementation).

    **P1 — Add keyed `deps`/`_build`/PLT caching (zero caching currently)**
    - Category: Performance
    - Issue: Every job runs `mix deps.get` from scratch and recompiles `_build` fully. No `deps`, `_build`, or Dialyzer PLT cache exists. Estimated 8×–9× wasted compile/fetch minutes per PR run.
    - Proposed change: Add `actions/cache` restore/save steps with precise keys (OS + OTP + Elixir + MIX_ENV + `mix.lock` hash + cache-buster). Restore keys allow partial hits. PLT uses split restore/save so a failing Dialyzer run still persists the PLT.
    - Expected impact: Warm-run PR wall-clock drops by estimated 60–70% on the `test` job (cold compile = ~300s; warm compile ~10–20s).
    - Risk: Stale cache can mask warnings — mitigated by strict key dimensions and keeping `mix deps.get` on cache-miss. `_build` must never restore across incompatible OTP/Elixir/MIX_ENV.
    - Rollback: Remove cache steps; revert to cold-compile. Immediate effect.
    - Target phase: 109.

    **P1 — SHA-pin `erlef/setup-beam` in ci.yml and release.yml (inconsistent supply-chain posture)**
    - Category: Security
    - Issue: ci.yml and release.yml use floating `erlef/setup-beam@v1`; hexdocs.yml is already SHA-pinned (`@8251c48...`). A compromised `@v1` tag could inject arbitrary code into all CI and release runs.
    - Proposed change: Pin to the same immutable SHA as hexdocs.yml; add Dependabot to auto-update action pins.
    - Expected impact: Eliminates supply-chain tampering via floating tag. Low friction — one-line change per workflow.
    - Risk: Very low. SHA pins are standard OSS posture. Dependabot keeps them fresh.
    - Rollback: Revert to `@v1` (one-line change per file).
    - Target phase: 112 (SEC-01).

    **P2 — Rationalize the release-proof job's presence on every PR (critical-path bottleneck)**
    - Category: Performance / Reliability
    - Issue: `release-proof` runs on every PR (`needs: test`, no trigger filter) and averages ~600s (~10min), making it the single biggest contributor to PR wall-clock. It runs `mix release.preflight` which includes `hex.build --unpack` + `hex.publish --dry-run` — correct for a release check but expensive for every PR commit.
    - Proposed change: Evaluate moving `release-proof` to push-to-main or scheduled; keep it on PR only if it catches bugs the `test` job doesn't. Phase 111 topology audit will make the final call.
    - Expected impact: If moved to main-only, PR wall-clock drops by ~10min; critical path becomes START → test (~6.5min) → Tier 2 without release-proof.
    - Risk: Medium — must verify `test` gate alone is sufficient for PR merge confidence. Don't weaken the release-proof; just tier it correctly.
    - Rollback: Move `release-proof` back to `needs: test` on PR trigger.
    - Target phase: 111.

    **P2 — Convert safe async:false modules to async:true (Phase 110 scope)**
    - Category: Performance / Test Quality
    - Issue: 34 explicit `async: false` modules (+ 4 with no setting). At least 3–4 residue modules (BrandingContractTest, IntegrationsContractTest, RecipesContractTest, ManifestTest) show no global-state mutation on human read — they may be `async: false` by convention, not necessity. Converting safe modules to `async: true` improves test parallelism.
    - Proposed change: For each module, confirm the async:false reason (cited in BASE-03); flip modules with no real reason; document remaining ones per D-04 evidence floor.
    - Expected impact: Potentially 3–5% wall-clock reduction on the test suite by increasing ExUnit concurrency.
    - Risk: Low if evidence-based. High if flipped blindly — global state leaks will cause intermittent failures. Bounded flake sweep (Phase 110 TEST-03) provides proof.
    - Rollback: Revert `async: true` to `async: false` per module.
    - Target phase: 110.

    **P3 — Add PR-level concurrency cancellation (superseded-run waste)**
    - Category: Performance / DX
    - Issue: No `concurrency:` group defined. Pushing a second commit to a PR triggers a new full CI run while the previous run is still in progress — burning runner minutes and producing a stale red/green signal.
    - Proposed change: Add `concurrency: group: ${{ github.workflow }}-${{ github.event.pull_request.number || github.ref }} / cancel-in-progress: true` at the workflow level; ensure `push` to main and tag runs are excluded from cancellation.
    - Expected impact: Eliminates wasted runner-minutes on superseded PR commits; reduces queue buildup.
    - Risk: Low. Well-understood GitHub Actions pattern. Must not cancel main or release runs.
    - Rollback: Remove `concurrency:` block.
    - Target phase: 111.

    **P3 — Dependency/security audit lane (`mix hex.audit` / `mix deps.audit`)**
    - Category: Security / DX
    - Issue: No dependency audit runs in CI. Known-vulnerable dependencies would not be flagged automatically.
    - Proposed change: Add `mix hex.audit` in a scheduled/nightly lane (not PR fast-path, to avoid coupling to flaky network calls).
    - Expected impact: Automated CVE detection for Hex dependencies.
    - Risk: Low. Network-dependent — correct to schedule, not PR-gate.
    - Rollback: Remove the audit step from the scheduled job.
    - Target phase: 112 (SEC-04).
